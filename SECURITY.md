# Scriba security

## Reporting a vulnerability

**Do not open public issues for security problems.**

Write privately to: **trombino.mario.ph@gmail.com**
Suggested subject: `[SECURITY] Scriba – short description`

Include, if possible:

- affected package and version (`@scriba-editor/core`, `@scriba-editor/sanitize-server`, …);
- description of the problem and its impact (e.g. XSS, code execution, access to other people's
  documents);
- steps to reproduce it or a minimal payload;
- browser / Node version used.

### What happens next

| Stage                         | Indicative time        |
| ----------------------------- | ---------------------- |
| Acknowledgment of receipt     | within 3 business days |
| First assessment and severity | within 10 days         |
| Fix and release               | depending on severity  |

Every fixed vulnerability gets a regression test in the security suite.
If you wish, you will be credited in the release notes once the fix is published.

## Supported versions

The project is in early development (`0.x`): security fixes are released only on the latest
published version.

## In scope

- XSS or code execution through content that is pasted, imported, loaded (`setContent`),
  received in collaboration or generated by the AI;
- bypassing the URL, tag or attribute whitelist;
- differences between the browser sanitization and that of `@scriba-editor/sanitize-server`
  (mutation XSS);
- freezes or excessive resource consumption (DoS) with contained input;
- unauthorized access to or modification of documents in real-time collaboration.

## Responsibilities of whoever integrates the editor

Sanitization in the browser is a convenience, **not a protection**: anyone can call your API
bypassing the editor. Before saving or displaying HTML coming from clients, **always** pass it
through `@scriba-editor/sanitize-server` with the same schema used in the editor.

The HTML produced can contain `style` attributes, but only **typed and validated** ones
(alignment, indentation, colors, font and size), never free-form styles. The editor applies
them via the CSSOM and works with a strict CSP. If the page that _displays_ the saved HTML uses a
CSP that forbids inline styles, those styles will not be applied: either you allow
`style-src-attr 'unsafe-inline'` on that page, or you accept rendering without styles.

If your CSP uses the `trusted-types` directive, add the `scriba` policy: it is only used to read
pasted HTML in an inert document, whose content goes through the schema parser anyway.

Validating uploaded files (real type, size, antivirus if needed) is also your server's job.

**Protected blocks** (`@scriba-editor/plugin-permissions`) only lock the editor. When you save a
document, compare the previous version and the new one with `checkBlockEdits` and reject the
save if it returns any ids. In collaboration, pass `canEditBlock` from `authenticate` and the
`schema` to the server: updates that touch a protected block are reverted for everyone. The name
shown in mentions is just text: always resolve the id on the server.

Someone who is **read-only but can comment** (`canComment`) can only add or remove comment
anchors: the collaboration server reverts every other change. If you save documents with your
own API, apply the same rule: compare before and after ignoring the annotation marks and reject
the save if the rest has changed.

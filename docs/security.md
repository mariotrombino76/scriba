# Security

> In plain words: the editor is the front door of a house. Everything that comes in (pasted
> text, loaded HTML, messages from other users, AI responses) is a stranger until it has been
> checked. And even if the door is secure, **the server must check again**, because someone can
> come in through the window: send HTML straight to your API, without going through the editor.

## The rule you never skip: re-sanitize the HTML on the server

Cleaning done in the browser is a convenience, not a protection. Before you **save** or
**display** HTML received from a client, pass it through `@scriba-editor/sanitize-server` with
**the same schema** as the editor:

```ts
// Node server (Express, Fastify, Nest… it works the same)
import { sanitizeHTML, InputTooLargeError } from '@scriba-editor/sanitize-server'
import { schema } from './schema.js' // the same one used in the browser

app.post('/api/note', (req, res) => {
  try {
    const clean = sanitizeHTML(schema, String(req.body.html ?? ''))
    save(clean)
    res.sendStatus(204)
  } catch (e) {
    if (e instanceof InputTooLargeError) return res.sendStatus(413)
    throw e
  }
})
```

`sanitizeHTML` uses `parse5` (no DOM, no code execution) and the same rules as the browser:
whatever the schema does not know is discarded. It also limits the input size
(`maxInputLength`, default 5 million characters) and the nesting depth.

If you save **JSON**, rebuild the document on the server with `schema.nodeFromJSON(json)`: it
throws an error for everything the schema rejects (types, attributes, URLs, depth).

## What the editor does

- **Schema parser for everything that comes in**: paste, initial content, `setContent`,
  opened files, source view, drag and drop, document templates, AI responses, collaboration
  updates.
  Parsing happens in an **inert document** (`DOMParser`): an `<img onerror>` does not fire,
  not even during parsing.
- **No `innerHTML`** and no `eval` in the code (enforced by ESLint with security rules).
- **Whitelisted URLs**: links only `http`, `https`, `mailto`, `tel` and relative, after
  normalization (entities, spaces, control characters). `data:` images only PNG, JPEG, GIF,
  WebP within a size limit; **never SVG**.
- **No free-form styles**: colors, alignments and sizes are typed attributes with strict
  validators; no `url()`, `expression()`, `@import`, `var()` from outside.
- **Attributes**: only those declared in the schema; all `on*` discarded; `id` handled to
  prevent DOM clobbering.
- **Links in a new tab** with `rel="noopener noreferrer"`.
- **Media**: an `<iframe>` only for the players of approved services (YouTube in
  privacy-enhanced mode, Vimeo, Dailymotion, Spotify, Google Maps), always with `sandbox`;
  `<video>`/`<audio>` only with an https or relative address, never `autoplay`; no other
  iframe, never `srcdoc` (details below).
- **Classes**: only the ones you list (`withBlockClasses`, `classMarks`), format
  `[a-z][a-z0-9-]*`, never `scriba-…`; all others are discarded.
- **Ids**: only with fixed prefixes (`anchor-`, `fn-`, `fnref-`) and a checked name or number,
  against DOM clobbering.
- **Merge fields**: `data-merge-tag` only with a name `[a-z0-9_.]`; the text inside is always
  rebuilt from the name. `fillMergeTags` inserts the values as **text**, never as HTML.
- **Formulas**: from incoming HTML, only the LaTeX source is read (the `application/x-tex`
  annotation); the MathML is always regenerated by KaTeX with `trust: false` (no `\href`,
  `\url`, `\includegraphics`, `\htmlClass`) and limits against recursive macros. Outgoing
  MathML uses only a whitelist of elements and attributes: never `maction`, `annotation-xml`,
  links, classes or styles. This way the known mutation XSS attacks via MathML never reach the
  document.
- **Collapsible sections** (`<details>`): only the `open` attribute; `ontoggle` and every other
  attribute are discarded.
- **Regex search** in a Web Worker with a time limit: a catastrophic regex does not freeze the
  page.

## CSP and Trusted Types

Scriba works with a strict Content Security Policy, without `unsafe-inline` or `unsafe-eval`:

```
default-src 'self'; script-src 'self'; style-src 'self'; img-src 'self' data: https:;
object-src 'none'; base-uri 'none'; require-trusted-types-for 'script'
```

- Dynamic styles go through the CSSOM (`el.style.width = …`), never through `style` attributes
  or injected `<style>` tags.
- With `require-trusted-types-for 'script'`, allow Scriba's policies:
  `trusted-types scriba scriba-worker` (the second one is for the search worker).
- If you load the script from a CDN, add its origin to `script-src` and use `integrity` (SRI).

The end-to-end tests all run with this CSP active.

**CSP reports from Chromium.** To read HTML that comes from outside (paste, source view,
`setContent`), Scriba opens it in an inert document. Chromium applies the page's CSP to that
document: if the HTML has `style` or `on…` attributes, it **blocks** them and reports it
(`style-src-attr`, `script-src-attr`), even though they would never have been used. This
applies to every inert document (`DOMParser`, `<template>`, `createHTMLDocument`,
`Document.parseHTMLUnsafe`); Firefox and Safari do not do this. It is not a successful attack:
it is an attack (or a Word style) that was stopped. If you collect reports with `report-uri` or
`report-to`, expect these entries when users paste from Word or from web pages. Do not add
`'unsafe-inline'` to make them go away: Scriba does not need it.

**WebKit and `<select>`.** Safari builds the internal parts of a `<select>` with inline styles,
which a strict CSP rejects (with an error in the console). This is why Scriba's dialogs use
radio buttons instead of drop-down menus.

### Embedded media and video/audio files

With `@scriba-editor/plugin-embed` the saved HTML can contain:

- an `<iframe>`, but only with the exact player address of an approved service: YouTube in
  privacy-enhanced mode (`www.youtube-nocookie.com/embed/…`), Vimeo
  (`player.vimeo.com/video/…`), Dailymotion (`www.dailymotion.com/embed/video/…`), Spotify
  (`open.spotify.com/embed/track|album|playlist|episode/…`) and Google Maps
  (`www.google.com/maps/embed?pb=…`). The editor always rebuilds the address from the checked
  reference and sets, itself, `sandbox="allow-scripts allow-same-origin allow-presentation"`,
  `referrerpolicy="strict-origin-when-cross-origin"` and `loading="lazy"`: everything that
  arrives with the iframe (other domains, `srcdoc`, `allow`, handlers, its own `sandbox`) is
  discarded, by `sanitize-server` too. In the editor the player is a card: the person writing
  does not contact the service.
- a `<video controls>` or `<audio controls>` with an **https or relative** `src` (never
  `data:`, `blob:` or `http:`); `autoplay`, `poster`, `muted`, `loop` and the other attributes
  are discarded, and of a `<source>` only the address is read. The uploaded file goes through
  **your** `upload` function: on the server, check the real type, the size and the content.

The pages that **display** the saved HTML must allow them in the CSP (`EMBED_FRAME_SRC` lists
the services):

```
frame-src https://www.youtube-nocookie.com https://player.vimeo.com https://www.dailymotion.com https://open.spotify.com https://www.google.com;
media-src 'self' https://your-cdn.example
```

## Image upload

The editor uploads nothing on its own: it calls **your** `upload(file)` function. The type and
size check in the browser is only a help for the user. On the server:

- check the **real type** from the first bytes of the file (not from the name or the
  `Content-Type`);
- limit the size; use an antivirus if needed;
- **reject SVGs** (they can contain scripts) or, if you really need them, sanitize them on the
  server and serve them with the correct `Content-Type` and `Content-Disposition: attachment`;
- serve images from a separate domain if you can.

**Photo editing** (crop, rotation, adjustments) produces a new file that goes through the same
`upload` function, with the same checks: treat it like any other uploaded file. Without
`upload`, the result becomes a raster `data:` URL within the schema limit. Images from another
site can be edited only if that site serves them with CORS (`Access-Control-Allow-Origin`): the
editor requests them with `crossOrigin="anonymous"`, without cookies; otherwise the dialog says
so and edits nothing.

## Saved versions

History versions (`@scriba-editor/plugin-revisions`) come from your server but are still
untrusted input: HTML goes through the schema parser in an inert document, JSON through
`schema.nodeFromJSON`; above 5 million characters the version is rejected. Author and label are
displayed as text. Check on the server who can read the versions of a document, as you do for
the document itself.

## Drafts in the browser

`@scriba-editor/plugin-autosave` saves the document in `localStorage` **in plain text**, on that
device: enable it only where that is acceptable (not on shared computers for sensitive data) and
call `clearDraft` after saving and on logout. A draft read from the browser is untrusted input:
it comes back only if `schema.nodeFromJSON` accepts it.

## Collaboration

Updates from other users are untrusted input: the client validates them against the schema,
and the server (`@scriba-editor/collab-server`) authenticates every connection, checks
permissions per document, limits message size and rate, and assigns **itself** the names and
authors of cursors and comments. Details in [Collaboration](collaboration.md).

## AI assistant

- The API key stays **on your server**: the editor only calls your `complete` function.
- Responses are untrusted input: text through the schema parser, blocks through `nodeFromJSON`
  plus a whitelist (no images, links only if allowed, no comments).
- The AI can only **propose undoable content**, which the user accepts or discards.
- The document may contain malicious instructions aimed at the AI (prompt injection): treat it
  as data in your backend and do not give the model tools that act outside the editor.

Details in the [AI guide](../packages/plugins/ai/README.md).

## Checklist for integrators

- [ ] HTML (or JSON) re-checked on the server with `sanitize-server` / `nodeFromJSON`, with the same schema.
- [ ] Upload: real type, size, no SVG.
- [ ] Strict CSP with Scriba's Trusted Types policies.
- [ ] Collaboration: an `authenticate` that really verifies the token and the per-document permissions.
- [ ] AI: key only on the server, rate and size limits, users informed.
